## High priority

- **Widened `games` RLS policy for `wishlist_public` technically permits wishlist rows through *any* games query, not just the gift list page** — noticed while building it (see `CHANGELOG.md`): the policy change is scoped to `ownership = 'wishlist'` rows only, and both existing views that query another user's `games` (`/compare/[username]`, the shelf mosaic) were checked and are safe — both already gate on `is_public` at the app level before ever running the query, so nothing leaks today. But any *future* feature that queries `games` for a non-owner without an explicit `is_public` check would now silently see that profile's wishlist items even when the profile is otherwise private. Worth keeping in mind rather than a build item on its own — flagging so it isn't a surprise later.
- **Worth watching: crowdsourced series matching now fetches every row of the item type, not just matches** — noticed while adding normalization to `lib/seriesCrowdsource.js` (see `CHANGELOG.md`): merging near-duplicate series names (punctuation/spacing differences) properly means comparing normalized text in JS, which can't be done as a server-side exact match — so it now pulls every row of that `item_type` and filters client-side instead of letting Postgres narrow it down first. Fine at today's scale (Funko Pops only, RLS-scoped to public profiles plus the viewer's own), but would need a real search index if this ever handled a type with meaningfully more rows.
- **Worth watching: the full release catalogue falls back to loose name matching for a platform IGDB can't resolve at all** — "owned" matching (`lib/platformCatalogueMatch.js`, see `CHANGELOG.md`) runs through real IGDB platform ids now, not free-typed name comparison, so common abbreviations ("PS2" vs. "PlayStation 2") match correctly. The one case this doesn't cover: a platform IGDB has no record of whatsoever — a genuinely obscure/regional/bootleg system — resolves to no id on either side, which falls back to the original loose substring comparison. Not expected to come up often (IGDB's platform coverage is broad), but worth knowing if a specific report of a missed match ever comes in.
- **Worth watching: IGDB franchise matching can still land on the wrong candidate, or find nothing at all, for a handful of titles** — confirmed live from real `refresh-upcoming-releases` cron output (Sep 2026, back when that cron still resolved franchises from owned titles — see the next bullet's note: Upcoming Releases moved off this path entirely in the genre/platform redesign, `CHANGELOG.md`). Still live and worth tracking because `lib/igdbSearch.js`'s `getFranchiseGames()`/`titleVariants()` remain in active use elsewhere (GameModal's "Series" section, `/api/igdb-franchise`). The title-spelling fallback added that round (`titleVariants()`) fixed the two confirmed spelling-mismatch cases — a camelCase-joined title typed with a space ("MegaMan X" → "Mega Man X") and a Pokémon version name typed as two words ("Pokemon Leaf Green" → "Pokemon LeafGreen"). Two different failure modes are still open, seen in that same log: a title with genuinely zero IGDB search results under any spelling tried ("FIFA Football 2005" — EA's UK-region name; IGDB may only list the NA "FIFA Soccer 2005" name, which no spelling-variant guess bridges), and a title that matches a real but wrong candidate among several similarly-named ones ("Lemmings" picking "LemminGS," an obscure Apple IIGS port, over the mainstream entries). Both are IGDB fuzzy-search limitations, not a Shelf Life bug — the "Series" section already degrades gracefully (a title that never resolves just shows no series section, same as before this round). Worth a candidate-ranking pass (e.g. preferring the candidate with cover art, more platforms, or a higher IGDB rating count over pure name-match order) if more real wrong-pick examples turn up.
- **Worth watching: a real reboot/remake sharing its exact name with the original entry can get silently collapsed away in "See full series" — found live checking a direct question ("if i add fable, will the new fable show there") rather than from a bug report.** (No longer affects Upcoming Releases — that feature moved off `getFranchiseGames()` entirely in the Sep 2026 genre/platform redesign, see `CHANGELOG.md`; this is now purely a "Series" section / `/api/igdb-franchise` concern.) `getFranchiseGames()`'s de-duplication (`lib/igdbSearch.js`, added Aug 2026 to stop "Grand Theft Auto V" showing 3-4 times for its PS3/PS4/PS5/Xbox rows) collapses every entry that shares the same normalized name, keeping whichever copy has cover art, then the earliest release year — which can't tell "the same release on another platform" apart from "an unrelated new game that happens to share the original's exact title," like the real 2027 Xbox Series X|S/PC/PS5 Fable reboot IGDB has on file under the bare name "Fable," identical to the 2004 original. Confirmed live: resolving "Fable III" (`/api/igdb-franchise`) right now returns the 2004 "Fable" in its franchise list but not the 2027 one — though it's not confirmed from here whether that's this dedup collision or the 2027 entry simply not carrying a franchise tag yet on IGDB's side (a very recently-added listing sometimes lacks full tagging) — both are plausible and I couldn't disambiguate without live cron-authenticated access. Not fixed this round: a reliable "same release, different platform" vs. "new game, same name" signal isn't available — a hard year-gap cutoff was considered and rejected, since a real re-release can legitimately span a similar gap (that GTA V case spans 2013-2022, ~9 years, and correctly needs to stay merged) and IGDB's `category` field (main_game vs. remaster/port) is already known to be unreliable in this codebase's own findings (see the Full release catalogue fix, `CHANGELOG.md`). Worth a real fix if a same-named reboot's absence from the Series section gets reported for real, once there's an actual case to verify against instead of a hypothetical one.
- **Worth watching: Upcoming Releases doesn't broaden comics the way it now broadens games (Sep 2026 redesign, see `CHANGELOG.md`) — a deliberate scope call, not an oversight.** Games are now recommended by genre/platform; comics are still tracked by exact series only. Comic Vine has no clean genre-equivalent taxonomy to match against (publisher is the closest signal, and even that would mean scanning a publisher's entire catalogue for upcoming issues rather than one known volume), and real comic usage is a small slice of the app today (6 owned comic issues across every user, confirmed directly against production) — not worth the extra Comic Vine API calls (a much lower rate limit than IGDB's) for so little payoff yet. Worth revisiting if comic usage grows enough that "just the series I own" starts feeling as narrow for comics as it did for games.
- **Worth watching: other filter/type-switcher controls that sit far above the content they affect could have the same off-screen-feedback problem the collection-screen pill fix (see `CHANGELOG.md`, "Fixed: the Video Games/Trading Cards/Consoles/Funko Pops filter pills...") just solved for `DashboardClient.jsx`.** That bug wasn't a logic bug at all — the filter genuinely worked, it just gave no visible feedback near the click because the thing it changed was below the fold, so it read as broken. Haven't audited whether any other page has the same shape (a filter/toggle control positioned well above a long results area it drives) — the Full release catalogue's platform filter and any future filter UI are the most likely candidates given how tall those pages can get. Not fixing speculatively; worth a look if a similar "this button doesn't work" report comes in anywhere else.
- **Import from Goodreads confirmed dead, not just deprioritized — the Book half of the old "Import from Goodreads / Discogs" line (Sep 2026).** Checked directly before building either half: Goodreads stopped issuing new developer API keys back in Dec 2020 and disabled most existing ones not long after (multiple independent sources confirm this, not just one stale blog post) — there's no live path left to pull someone's Goodreads shelf in automatically. The Discogs half shipped instead and is confirmed working in production (see `CHANGELOG.md`, "Import from Discogs" — token configured, migration run, a real successful API call confirmed via Vercel logs). If a Books-import feature is ever wanted, it'd need a different source entirely (Open Library, which already powers Books' own search/auto-fill, has no per-user "shelf" concept to import from — this would really mean "import from a CSV/export file a user already has," not a live account-based pull like Steam/Discogs).

A suspected sixth instance (a `components/SeriesModal.jsx` file, thought dead per an earlier `CHANGELOG.md` entry, that still appeared to exist) turned out to be a stale file left over in the cloud sandbox's own uploaded snapshot of this repo, not a real regression — confirmed via `git log` against your actual Mac that it's genuinely gone there. Listing this whole thread as a closed loop again, not an open item — but see the next entry below for one real gap the same round turned up that *does* need a deliberate follow-up, and the audit approach itself (grep for "one type/currency/status assumed, several exist") is still worth repeating occasionally as the app grows.
- **`price`/`asking_price`/`price_alert_threshold` have no stored currency of their own — changing Settings > Currency silently relabels old entries under the new symbol instead of flagging them as stale.** Found in the same Sept 2026 audit round as the bulk-ownership fix above. `market_price` already has a `market_price_currency` companion column specifically so `GameCard.jsx` can detect and show a "(GBP)"-style mismatch warning when a frozen price-check snapshot no longer matches your current profile currency (see the "Worth watching" note this file already carries about live conversion being a separate, bigger gap). `price`, `asking_price`, and `price_alert_threshold` never got the same treatment — `GameCard.jsx`'s "For sale · {symbol}{asking_price}" badge and `GameModal.jsx`'s "Purchase price"/"Asking price"/"Notify me if price drops below" field labels all just read whatever your *current* profile currency is and slap that symbol on the stored number. Concretely: enter a Purchase price of 45 while your currency is GBP (meaning £45), later switch Settings > Currency to USD, and every card and the edit form now shows "$45" — the same number, silently relabeled as a different currency, with none of `market_price`'s "mismatched" warning. Real design work, not a quick patch: needs new `*_currency` columns (plus a migration/backfill decision for existing rows — freeze at entry time the way `market_price_currency` does, or assume everything pre-dating the column was entered in whatever the row's *current* currency happens to be, which isn't necessarily true), then updating both `GameCard.jsx`'s and `GameModal.jsx`'s display logic to read the stored currency instead of the live one and flag a mismatch the same way `market_price` already does.

## Later (bigger, more design work)

- **Shared/household collections** — let a second account co-manage one collection. Real permission/ownership questions to work through, not a quick add.
- **Multi-language support (i18n)** — everything's English-only, fine for a friends-and-family project but a real ceiling for an actual App Store product. Worth it once there's a specific market to justify it.
- **AI shelf-photo bulk import** — one photo of a physical shelf, detect and suggest multiple items at once instead of searching or typing each one in by hand. The most speculative idea here — accuracy on a photo full of spines needs real testing before promising it works.
- **Live currency conversion — narrowed to what's left.** The leaderboard piece is done (see `CHANGELOG.md`): the "Most valuable" podium now shows a converted figure alongside each collector's own-currency total — in the viewer's own preferred currency (Settings > Currency), not a fixed USD — using the exact rate data the ranking itself already sorted on. Still open: everywhere else display stays raw-currency-only (your own dashboard total, a public profile's "Collection value" stat, per-item prices) — real conversion there needs the same "what's the true underlying value" product call this line always flagged, since (unlike the leaderboard, which only ever needed one converted number to sort by) changing what a total *displays* touches something someone might actually budget against.
- **Xbox / PlayStation account integration** — Steam is done. Xbox is gated behind app registration; PlayStation has no official public API at all (reverse-engineered access only, fragile and ToS-gray-area).
- **Global chat** — a site-wide message board, separate from per-profile comment walls. Needs real-time updates and real moderation once it's not just friends talking.
- **More Shelf Life milestone variety — narrowed to what's left.** Platform-completionist, genre-breadth, and 5 oddball badges (tagging, notes, condition photos, for-sale, sold) all shipped (see `CHANGELOG.md`). Still open: decade-spanning badges — `games` has no original-release-date field to compute a decade from (only `purchase_date`, when *you* bought it, not when the item itself came out), so this would need per-item release-year enrichment from IGDB/Comic Vine/etc. stored on the row, a real schema addition, not a quick follow-up.
- **Even more collectible types** — board games, action figures/toys, coins, Lego sets, whenever there's demand.
- **iPad-specific polish** — the app went in as a Universal build (phone layout scaled up); a real iPad layout would be a nice follow-up if iPad usage turns out meaningful.
- **Native ad revenue from the app itself (AdMob)** — even with AdSense on for the website, the app earns $0 on its own; real native integration (AdMob SDK or Google's WebView Ads API) needs genuine Swift/native work. Not worth it at current traffic.
- **In-app marketplace: sell to another collector directly, not just an affiliate redirect** — distinct from the affiliate "buy it" links and the "For sale" flag, both already shipped (see `CHANGELOG.md`): those point outward or just show interest, this would be an actual listing another collector could act on inside Shelf Life. Real trust, payment, and dispute questions come with that — easily the biggest-scope item on this list. Worth starting with "list for sale + a way to message the seller" long before anything resembling in-app payments.
- **Native home-screen widgets (iOS/Android)** — today's stats, Play Next, or trophy progress right on the home screen, now that the app is wrapped for both platforms. Needs genuine native work (WidgetKit on iOS, App Widgets on Android) — same caveat as AdMob above, not buildable from this codebase alone.
- **Browser extension: add an item while shopping** — a small "Add to Shelf Life" extension that captures a title/price/image straight off an eBay/Amazon/retailer listing page instead of typing it in from memory later. A genuinely new platform surface — its own codebase, its own store listing and review process (Chrome Web Store this time, not Apple's or Google's).
- **Community-verified master sets** — master-set data currently comes entirely from TCGdex/Comic Vine/IGDB, or Shelf Life's own crowdsourced logs; a "flag this as wrong" or trusted-contributor correction layer would start to matter once master sets cover enough collectible types that data errors actually show up. Same flavor of real moderation/trust question as Global chat above.
- **Real sold-price data, not just current listings** — same competitor pass: Collectr and TCGplayer both lean on actual transaction/sold-price data as their credibility anchor for "what's this actually worth." Shelf Life's own eBay price check is explicitly current active-listing prices, not sold comps (a known, already-documented limitation — see `CHANGELOG.md`), because eBay stopped offering free access to sold-listing data. Flagging honestly rather than pretending it's a clean build: closing this gap for real needs either a paid market-data source or something against eBay's ToS, so it's more of an "if the budget ever supports it" item than a normal build.
- **Upcoming Releases for the remaining collectible types** — checked while building the Upcoming Releases page (Sep 2026, see `CHANGELOG.md`): games and comics are covered (IGDB/Comic Vine both expose real future dates). Trading cards are the only other type where this might be reachable — Scryfall and TCGdex both have a real release-date field on their Set objects — but two real open questions before it's worth attempting: (1) neither's docs confirm whether a not-yet-released set is actually listed ahead of time the way IGDB/Comic Vine list unreleased games/issues, only that the field exists on sets that have already released, and (2) the feature shape is genuinely different from games/comics — you can't own a card from a set that hasn't released yet, so "upcoming" here would have to mean "a new set is coming for Pokémon/Magic, the TCG(s) you collect," not "the next item in a series you already own," which is a coarser per-TCG signal rather than a per-series one. Funko Pops, Vinyl, CDs, DVDs, and VHS have no path at all — same wall already hit for master-set/series lookups on these types (see `lib/seriesCrowdsource.js`'s module comment and the "Real master sets" entries in `CHANGELOG.md`): no free, live, per-item database exists for any of them, so there's no future-date field to even check. Books now has a real per-author backend (Open Library, see `CHANGELOG.md`'s "Books: a real bibliography" entry) but that doesn't automatically unlock this — Open Library is a catalog of already-published books, not a preorder/forthcoming-titles tracker the way IGDB/Comic Vine are, and whether its author-works data reliably flags a not-yet-published title at all hasn't been checked. Not worth building on a guess; worth revisiting trading cards specifically if either API's actual behavior around unreleased sets ever gets confirmed, checking Open Library's forthcoming-title coverage for real before attempting Books, or if a new source appears for the rest.
- **Creator/contributor pages — browse everything by an author, artist, developer, director, etc., Fantastic Fiction-style — requested directly (Sep 2026), same message that flagged the full release catalogue's click-through and layout issues above.** **Comics shipped (Sep 2026, see `CHANGELOG.md`) — `/creator/comics`, linked from the footer.** Public (you picked this directly when asked — the one real open question the original version of this entry flagged as undecided), signed-out and signed-in both work, ownership-highlighting and click-to-price-check on missing issues once signed in. **Books shipped next (Sep 2026, see `CHANGELOG.md`) — `/creator/books`, also linked from the footer** — same public, signed-out-and-signed-in shape, built on the existing Open Library author-bibliography backend directly rather than any new API integration. **Games shipped last (Sep 2026, see `CHANGELOG.md`) — `/creator/games`, also linked from the footer** — same shape again, this time by developer/publisher rather than an individual person, built on a new `lib/igdbCompanyLookup.js` module against IGDB's existing companies/involved_companies data (no schema change to the `games` table, per this entry's own earlier read). All three now cover every item type worth covering here — see below for the ones deliberately left out. Structurally none of the three was a new pattern — each turned an existing per-type series/master-set feature (or, for Games, the existing IGDB company data the Full release catalogue's own module already showed was reachable) into its own standalone, searchable destination instead of only reachable from inside one already-owned item's detail view.

  Deliberately not covered, same per-source feasibility read that ruled each one out when this entry was still open:
  - **Trading cards — plausible for Magic, unconfirmed for Pokémon.** Scryfall (Magic, already integrated) has a real per-card `artist` field and a documented `artist:` search operator. Whether TCGdex (Pokémon) exposes an equivalent illustrator field reliably enough to search on isn't confirmed from here — same "couldn't verify against live data from this sandbox" caveat every external API integration in this codebase carries until checked for real. Worth revisiting if that ever gets confirmed.
  - **Vinyl, CD, DVD/VHS — crowdsourced only, the same wall their existing series feature already hit.** No free, live, per-item database exists for any of these (see the "Real master sets" and Upcoming Releases entries above) — a creator page here would only ever show what other Shelf Life users have already logged under that same artist/director name (`lib/seriesCrowdsource.js`'s existing cross-user matching), which could be genuinely sparse on a small user base. Worth shipping as an honest "here's what other collectors logged," not oversold as a real discography/filmography, if this ever gets prioritized.
  - **Funko Pops and consoles — likely out of scope**, same reasoning `lib/seriesLookup.js` already uses to leave consoles out of the series feature entirely: their `publisher` field is a manufacturer or an exclusivity partner, not an individual creator — grouping by it is a category, not an "everything this person made" list.

## Paid / premium ideas (business decisions, not just builds)

Everything Shelf Life does today is free, and there's no payment processor wired up anywhere in this codebase — before any single idea below is buildable, that has to exist first: most likely Stripe given the Next.js/Vercel/Supabase stack, plus a `subscriptions` table, webhook handling, and an entitlements check gating whichever features end up behind it. That's real work on its own, on top of the actual pricing/tier design, which isn't something I can decide — these are flagged here as ideas worth having on file, not prioritized or sequenced like the tiers above.

- **A Pro subscription tier** — the prerequisite for everything else in this section (payment processor + entitlements, described above). Worth deciding what actually goes behind it before building any of it — probably some mix of the ideas below rather than one single "upgrade" button.
- **Real sold-price data** — already flagged in the "Later" tier above as a known gap (Shelf Life's eBay price check is current listings only, since eBay stopped offering free access to sold-listing data). A paid collectibles pricing API (PriceCharting, CardLadder, or similar) could close it for real, but the ongoing per-lookup cost only pencils out behind a Pro tier or a pass-through charge.
- **PSA/CGC population data for graded items** — already a Medium-priority idea (trading cards/comics already have a Grade field; showing how rare that exact grade is would be a nice addition). The reliable, complete population-lookup data on PSA's/CGC's own side tends to sit behind their own paid tiers, so this is really the same "needs a paid upstream data source" shape as sold-price data above.
- **AI photo/shelf auto-fill** — already flagged elsewhere in this file as blocked without a new AI vision API key (nothing like that is configured today, and it'd carry a real per-call cost). A natural Pro-tier perk once billing exists, rather than something offered free to every account.
- **Collection appraisal/insurance PDF export** — the free version has already shipped (see `CHANGELOG.md`: a print-optimized `/dashboard/appraisal` page). A paid tier could go further — an actual generated PDF file (not just print-to-PDF) with a real letterhead/signature block, or bundling in condition photos per item — rather than gating the basic export itself.
- **Boosted/featured "For sale" listings** — the "For sale" flag itself has shipped (see `CHANGELOG.md`); once the in-app marketplace (Later tier) also ships, a "boost this listing" placement — similar spirit to eBay's promoted listings — would be a natural, low-effort monetization hook layered on top of features that are already worth building for their own sake.
- **Bigger photo/storage limits** — condition photos are capped at 4 per item today; Supabase Storage cost scales with actual usage, so a Pro tier raising that cap (more condition photos, higher-res uploads) ties a real infra cost directly to a real, easy-to-understand perk.
- **Ad-free browsing for logged-in users** — AdSense on the website is already planned but not yet live (see the "Needs a quick action from you" section above). Once it is, removing ads for paying accounts is a standard, low-build-effort Pro perk to pair with it.
- **A vanity profile handle or "verified collector" badge** — purely cosmetic, no ongoing cost once billing exists, and the safest first thing to ship behind a Pro tier before committing to any of the pricier, ongoing-cost ideas above.
- **Public read-only API access — narrowed now that it's shipped (see `CHANGELOG.md`).** Personal access tokens for pulling your own collection into a spreadsheet, dashboard, or script are live today, free, rate-limited to 60 requests/minute per token. Still open: whether a higher/uncapped rate limit (or usage past some volume) should become a Pro perk rather than staying free for every account — a real ongoing-infra and support-surface question, worth deciding deliberately rather than assuming either way.
